## 7. Invalid or imprecise machine-readable data

**The Icebreaker's `startDate` is `"2025-10"` — a month, not a date.**

- Valid **ISO 8601**, and valid **schema.org** (`Date` permits reduced
  precision).
- **Not accepted by Google's Event rich-results**, which requires a full date
  and will drop the event from rich results — the block is inert rather than
  harmful.
- The public display "October 2025" / "Październik 2025" is correct and must be
  preserved either way.

The proposed schema handles this with `date_precision: month`, so the renderer
knows to print "October 2025" and can decide independently whether to emit
JSON-LD. **No exact day may be invented.** → **Decision 2.**

All other dates are valid full ISO dates. Start/end ordering is correct
everywhere; only the Business Forum has an `endDate` (`2026-04-24` →
`2026-04-25`), correctly ordered.

## 14. Proposed canonical schema

Two layers — see the worked examples in
[`schema-examples/`](schema-examples/):

**Shared event core** (every event, including the Forum): `slug`,
`event_family`, `template`, `academic_year`, `published`, `order`,
`show_in_listing`, `show_in_timeline`, `show_in_archive`, `flagship`,
`start_date`, `end_date`, `date_precision`, `venue{name,locality,country}`,
`hero_image`, `og_image`, `gallery`, `organiser`, `co_organisers`,
`performers`, `registration`, `instagram_permalink`, `album_url`,
`external_links`, `downloads`, plus `en:`/`pl:` blocks carrying `title`,
`hero_eyebrow`, `card_summary`, `timeline_summary`, `intro_copy`, `body`,
`facts`, `album_label`, `seo_title`, `seo_description`, `jsonld_description`.

**Business Forum extension** — a `business_forum:` block present only on that
family: `edition_number`, `edition_ordinal`, `branding`, `statistics`,
`people`, `partner_categories`, `funding_acknowledgement`, `forum_ball`,
`photographers`, `call_to_action`.

### Nested extension vs separate file — recommendation

**Recommended: nested `business_forum:` block inside the annual event record.**

| Criterion | Nested block | Separate side-file |
| --- | --- | --- |
| One canonical annual edition | ✅ one file | ❌ two files to keep in step |
| Decap CMS | ✅ one entry, conditional fields | ⚠️ two collections, manual linking |
| Avoids a giant generic schema | ✅ the block is family-scoped | ✅ |
| Standard-event form stays simple | ✅ block absent entirely | ✅ |
| Forum fields can't leak onto standard events | ✅ validator rejects the key | ✅ |
| Validation and type safety | ✅ one document to validate | ⚠️ cross-file references |

The side-file's only real advantage is file size. The nested block wins on the
criterion that matters most here — **one canonical record per edition** — and
avoids a class of bug where an event record and its Forum data disagree about
which edition they describe.

### Display dates are generated, not stored

`card_display_date` and `timeline_display_date` are currently written by hand in
four places per event per language. Every one of them is derivable from
`start_date` + `end_date` + `date_precision`, using the same locale-aware
formatter the announcements already use. No localised display date is stored.

The one case needing care is the Business Forum's "24–25 April 2026" /
"24–25 kwietnia 2026" range and the Icebreaker's month-only "October 2025" —
both are formatting rules, not stored strings. An explicit
`date_display_override` is **not** proposed, because no current value requires
one; if one ever does, it should be added then and documented.

**Recommendation: no change now, year-suffix new editions.** Keep

sitemap and every announcement link. Give the *next* edition
`business-forum-2027`. The cost is a slight asymmetry; the alternative is
breaking existing URLs to buy tidiness. → **Decision 12.**

## 17. Registration and payments boundary

**In scope** — content fields only:

```yaml
registration:
  state: none | open | closed | sold-out
  type: null | external-link | payment-link | email
  url: "https://…"
  email: "…@polsocfederation.pl"
```

A marketing officer can set the state and paste a link. That is the whole
feature.

**Explicitly out of scope, and IT-led when wanted**: native attendee
registration, Stripe or any payment webhooks, an attendee database, waiting
lists, ticket inventory, confirmation emails. None of these is a content
problem, and none should be approximated with content fields.

No current event has a registration link — all five are past — so this model is
designed from the stated requirement, not reverse-engineered from markup.

## 19. Remaining limitations

- **The audit reads the live pages, not a specification.** Where all sources
  agree it cannot tell whether they agree on something *correct* — only that no
  source contradicts another.
- **Announcement records were inventoried but not reconciled** against event
  facts. They are news items about events, not descriptions of them; merging
  them would import editorial copy into structured data.
- **`eventStatus` variation is unmodelled.** All five events are
  `EventScheduled`; a postponed or cancelled edition has no field yet.
- **Business Forum multi-edition rendering is untested** — the template will not
  exist until the implementation phase, so the extension schema is validated as
  YAML only.

## Human decisions required before migration

Thirteen items. Each states what the system found, why it cannot choose, and
what follows from each option.

---

**1. Polish `og:image:alt` is English on four of five event pages**
*Event:* all except icebreaker · *Field:* `og:image:alt` (Polish pages)
*Sources:* `pl/event-business-forum.html`, `pl/event-sikorski-debate.html`, `pl/event-christmas-dinner.html`, `pl/event-youth-congress.html`
*Why the system cannot choose:* writing Polish alt text is authoring content, not reconciling it.
*Options:* **(a)** Translate all four during migration — recommended; the icebreaker page proves translation is the intent. **(b)** Reproduce the English text verbatim and fix later — preserves exact equivalence but ships a known defect into the new system.
*Consequence:* (a) means the generated Polish pages will *not* byte-match the live ones on this field, and `compare-events` must record it as an intentional difference.

---

**2. Icebreaker has a month-only date (`2025-10`)**
