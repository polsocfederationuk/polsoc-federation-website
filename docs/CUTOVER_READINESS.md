The inventory is **derived**, not hand-listed: static pages come from their
generating template (`src/index.njk`, `src/events.njk`, …) and event pages from
`content/events/*.yaml` filtered on `published: true`. Deleting a template or
unpublishing an event removes its route automatically.

It is deliberately **not** a scan of `dist/**/*.html`. A scan would publish a
diagnostic or fixture page the moment one appeared; requiring a route to be
declared makes adding one a deliberate act.

Note on visibility flags: `published` decides whether a page *exists*;
`show_in_listing` / `show_on_homepage` decide only whether it is *advertised*. A
published event hidden from the listing still has a real, indexable URL, and the
inventory reflects that.

## 3. Sitemap semantic differences

**One**, enumerated and asserted in both directions by `compare:sitemap`:

| | Live | Generated |
| --- | --- | --- |
| `<lastmod>` | `2026-07-27` on all 22 URLs | **omitted** |

The live value is a single hand-set date, not a per-URL content date. There is no
authoritative deterministic date to replace it with — most of these pages have no
content date at all — and the permitted alternatives (build time, file mtime,
current date) would each make the sitemap non-deterministic *and* assert something
untrue on every deploy. Omitting the field says nothing rather than something
false.

**Preserved exactly**: all 22 URLs, their order, `<changefreq>` and `<priority>`
per URL. The live weighting is a consistent, evidently intentional tier model
(homepage 1.0, listings 0.9, detail pages 0.6–0.8, every Polish route one step
below its English pair) and a cutover is the wrong moment to change a published
signal.

**No `xhtml:link` hreflang alternates**, in either file. Every page already carries
a reciprocal hreflang trio with an English `x-default` in its `<head>`, which is
the canonical place for it; duplicating that in the sitemap would be a second
thing to keep consistent for no gain. Partial or inconsistent sitemap hreflang
would be worse than none, so this is all-or-nothing and the answer is none.

## 5. Manifest and favicon handling

`site.webmanifest` and `favicon.ico` are **byte-identical passthroughs**. The
manifest is not redesigned or renamed.

Validated by `crawl:dist`: valid JSON; `start_url` and `scope` are `/`; `display`
is `standalone`; theme and background colours unchanged; all **3** icons exist in
`dist/`, are root-relative, carry the declared MIME type, and none uses a `/pl/`

## 6. Deployment-tree allowlist

`scripts/audit-dist.js` (`npm run audit:dist`) — **15/15 checks**, 180 files.

Rules are **category and reference based**, so a new photograph needs no edit here:

- **HTML** only at a known route (or a known noindex 404).
- **Root-level non-HTML** only from `favicon.ico`, `site.webmanifest`,
  `robots.txt`, `sitemap.xml`.
- **Assets** by directory and extension: `css/*.css`, `js/*.js`,
  `assets/**` (image types), `pl/**.html`.
- **Every asset must be referenced** by something in the tree. Orphans fail —
  unreferenced files in a deployment tree are dead weight or a mistake. References
  are collected from HTML attributes, `<meta content>`, JSON-LD, CSS `url()`,
  `srcset`, manifest icons and **JS string literals** (announcement and member
  images are referenced only from JS data), and same-domain absolute URLs count as
  local.

Fails outright on: `build-test/`, `docs/`, `content/`, `src/`, `scripts/`,
`node_modules/`, `.git/`, `.github/`, `.claude/`, `.fixtures/`, `test*/`, `tmp/`;
`package.json`, `package-lock.json`, `netlify.toml`, `eleventy.config.js`, README,
LICENSE; any `.yaml`, `.yml`, `.njk`, `.md`, `.ts`, `.log`, `.bak`, `.orig`,
`.swp`, `.lock`; `.DS_Store`, `Thumbs.db`, dotfiles, trailing-`~` backups,
unexpected source maps, and **zero-byte files**.

## 7. Removed fixture behaviour

`dist/build-test/` **no longer exists in a normal build.**

A normal build adds `src/build-test/**` to Eleventy's ignore list, so the fixtures
are not input at all. `BUILD_FIXTURES=1` inverts it: only the fixtures build, and
the output directory becomes `.fixtures/` instead of `dist/`. `npm run
build:fixtures` (via `scripts/build-fixtures.js`, a wrapper because `VAR=x cmd` is
not portable to Windows shells) does that.

`npm run test:archive-ui` — **35/35 checks** — builds the fixture, asserts the
archive CSS exists and is scoped to `.event-archive*`, asserts the fixture markup
still matches what `src/events.njk` actually emits (otherwise it would stop testing
anything), asserts the fictional events reach neither `content/events/` nor
`dist/`, and then **deletes `.fixtures/`**. Archive CSS coverage is unchanged.

`.fixtures/` is gitignored and removed by `npm run clean` alongside `dist/`. The
Phase 2 proof pages and Phase 3 chrome pages moved there too; `compare:chrome` and
the validator read them from `.fixtures/`, and the validator builds them once at
the start of its run.

## 14. Exact cutover procedure

1. On a branch, with a clean tree, run the full suite (§15 of the phase brief).
   Everything must be green.
2. Change `netlify.toml` — **two lines, not one**:

```toml
[build]
  command = "npm run build"
  publish = "dist"
```

> **The build command is not optional, and this is the single most dangerous
> detail of the cutover.** Verified in this phase: `netlify.toml` currently has
> **no `command`** (only a comment mentioning one), and `dist/` is **gitignored and
> untracked**. Netlify clones the repository, finds no `dist/`, runs no build, and
> publishes an empty directory — **the site goes down**. Changing `publish` alone
> is not a partial cutover, it is an outage.
>
> Eleventy, js-yaml and markdown-it are already `devDependencies`, so Netlify's
> default `npm install` provides everything `npm run build` needs. Confirm
> Netlify's Node version is 18+ in site settings before deploying.

3. That commit must contain **nothing else** — no sitemap, template, content or CSS
   work. Those two lines are one atomic change: reverting them restores the
   previous serving behaviour exactly.
4. Deploy to a **preview**, not production. Run the §16 checks against the preview.
5. Promote to production only after the preview passes.

## 15. Exact rollback procedure

1. Revert the cutover commit (`git revert <sha>`), restoring:

```toml
[build]
  publish = "."
```

2. Push, and let Netlify build and deploy that commit.

Do **not** rely solely on Netlify's UI "publish previous deploy". That changes what
is served without changing what is in the repository, so the next push silently
re-deploys the broken state. The revert commit is the durable fix; the UI rollback
is at best a stopgap while the revert lands.
