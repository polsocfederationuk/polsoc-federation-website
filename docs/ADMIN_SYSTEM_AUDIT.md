# Architecture audit: adding a Git-based Decap CMS

**Status:** audit only — nothing implemented, no files changed.
**Date:** 27 July 2026
**Scope:** what a CMS + static generator would have to take over, and what it must not break.

---

## 0. Executive summary

The site is 24 hand-written HTML pages (12 English at the root, 12 Polish under
`/pl/`) plus four JavaScript data files. Two content types are already
data-driven and would migrate almost mechanically. Two are pure HTML and are the
real work.

| Content type | Where it lives now | Instances | CMS readiness |
|---|---|---|---|
| Announcements | `js/announcements-data.js` + `js/pl/…` | 28 × 2 | **Ready** — already a clean array of objects |
| Member societies | `js/societies-data.js` + `js/pl/…` | 30 × 2 | **Ready** — flat records |
| Team members | hardcoded in `team.html` + `pl/team.html` | 21 × 2 | Needs extraction |
| Events | hardcoded across **6 places each** | 5 × 6 | **Hardest** — see §4 and §7.1 |

The single most important finding is in §7.1: **one event is currently described
in six separate locations**, and there is no mechanism keeping them consistent.
That is the strongest argument for the CMS, and also the biggest migration risk.

## 1. Where content is stored today

### 1.1 Events — hardcoded, six locations per event

There is no event data file. Each event exists as duplicated prose in:

1. `event-<slug>.html` — the detail page (long-form body, galleries, JSON-LD)
2. `events.html` — a summary card (`<article class="event-card">`)
3. `index.html` — a one-line timeline entry (`.tl-item`)
4. `pl/event-<slug>.html`
5. `pl/events.html`
6. `pl/index.html`

Plus, for most events, a related entry in both announcement data files.

The five slugs are `business-forum`, `sikorski-debate`, `christmas-dinner`,
`youth-congress`, `icebreaker`.

The existing `events.html` even carries an HTML comment instructing the editor to
copy-paste a card block and duplicate an `event-*.html` file by hand. That is the
current "CMS".

### 1.2 Announcements — JavaScript data, already structured

`js/announcements-data.js` exports `const ANNOUNCEMENTS = [...]` (28 objects,
newest first), consumed by inline JS in `announcements.html`, which builds cards
and a modal. The Polish twin is `js/pl/announcements-data.js`, loaded by
`pl/announcements.html`.

### 1.3 Team — hardcoded in one page per language

21 `.member` blocks in `team.html`, grouped into six `.team-section` containers
with matching filter chips:

| `data-group` | Heading | Members | Roles used |
|---|---|---|---|
| `trustees` | Trustees | 5 | President, Vice-President, Treasurer & Head of Partnerships, Head of Marketing, Head of Legal |
| `partnerships` | Partnerships Officers | 4 | Partnerships Officer |
| `events` | Events Officers | 4 | Events Officer |
| `marketing` | Marketing Officers | 3 | Marketing Officer |
| `legal` | Legal Officers | 1 | Legal Officer |
| `regional` | Regional & Operations | 4 | North Executive, South Executive, IT Officer, Institutional Relationships Officer |

One member (Stefan Gayda-Pimlott) has **no photo by design** and renders the
`<div class="ph" data-label="Headshot">` placeholder instead of an `<img>`. The
schema must allow a null photo.

### 1.4 Member societies — JavaScript data

`js/societies-data.js` exports `const SOCIETIES = [...]` (30 objects), consumed by
inline JS in `members.html` that builds Leaflet pins and cards.

### 1.5 Other hardcoded content (out of scope for v1, but noted)

- `index.html`: 4 testimonial `.quote-slide` blocks, 4 `.stat` counters, 3
  `.pillar` cards, 18 partner logo tiles (9 + 9 duplicated for the marquee loop)
- `contact.html`: address block, social handles, two "initiative" sub-cards
- `members.html`: 4-question FAQ accordion
- every page: header, nav, footer, language switcher (identical chrome × 24)

## 2. Hardcoded vs JavaScript-loaded

Only two pages load external data:

| Page | Script |
|---|---|
| `announcements.html` | `js/announcements-data.js` |
| `members.html` | `js/societies-data.js` |
| `pl/announcements.html` | `../js/pl/announcements-data.js` |
| `pl/members.html` | `../js/pl/societies-data.js` |

Everything else is static markup. `js/main.js` is shared behaviour only (reveal
animations, counters, carousel, timeline rail, mobile nav) and holds **four UI
strings** in a dictionary keyed off `document.documentElement.lang`:

```js
const UI = { en: {...}, pl: {...} }[document.documentElement.lang === "pl" ? "pl" : "en"];
```

Card labels generated by *inline* page scripts (`Read more →` / `Czytaj więcej →`,
`Sign-ups closed` / `Nabór zakończony`, the `E-mail`/`Instagram` buttons on the
members map) live inside each HTML page, so they are currently translated by
virtue of the page being translated. A generator must template these.

## 3. Field inventory

### 3.1 Announcement (28 entries, measured)

| Field | Present | Type / notes |
|---|---|---|
| `date` | 28/28 | Display string, **localised**: `"7 July 2026"` / `"7 lipca 2026"`. Not machine-readable — see risk §7.4 |
| `title` | 28/28 | string |
| `subtitle` | 28/28 | string, one-line teaser |
| `image` | 28/28 | path **or `null`** (3 entries are deliberate no-photo cards) |
| `body` | 28/28 | string, `\n\n` = paragraph break, may contain `<a>` HTML (1 entry does) |
| `link` | 11/28 | `{ href, text, external? }` — `external: true` on 2 |
| `closed` | 8/28 | boolean → "Sign-ups closed" chip |
| `imagePos` | 5/28 | CSS `object-position` |
| `fit` | 4/28 | `"contain"` for logo-style covers |
| `extraImages` | 3/28 | array of paths, shown under the body |
| `bg` | 1/28 | background colour behind a `contain` logo (`#001f62`) |

**Path conventions that must be preserved:**
- `image` / `extraImages` are **root-relative** (`/assets/...`) so the same value
  works from `/` and `/pl/`.
- `link.href` is deliberately **relative** (`event-business-forum.html`) so each
  language resolves to its own event page. Making it root-relative would send
  Polish readers to the English site.

### 3.2 Member society (30 entries)

`name`, `uni`, `lat`, `lng`, `instagram` (handle only — URL built at render),
`email` (empty string for 3), `logo` (bare filename in `assets/polsocs/`),
`active` (false for 1), `member` (true for 3), `pastMember` (true for 13).

`active` / `member` / `pastMember` are stored but **not rendered** — chips were
built and then removed by request. Keep the data, keep it unrendered.

Only `uni` differs between languages (`"Edinburgh, Scotland"` →
`"Edynburg, Szkocja"`). Everything else must stay byte-identical or the two maps
diverge.

### 3.3 Team member

`photo` (or null), `alt`, `role`, `name`, `email` (`firstname.surname@…`,
accents stripped), `linkedin`, plus the parent `group`.

Polish role titles are **grammatically gendered** and currently matched to the
individual (`Szefowa ds. marketingu`, `Specjalistka ds. relacji instytucjonalnych`).
The schema must treat role as a free-text localised string, not an enum shared
across people.

### 3.4 Event

Derived from the detail pages; no canonical record exists today.

Facts bar (`.fact` label/value pairs): 4 on the Business Forum
(Date, Venue, Attendance, Edition), 3 on the others (Date, Venue, and one of
Attendance / Format / In collaboration with).

JSON-LD `Event` fields actually emitted:

| Page | Fields |
|---|---|
| business-forum | `@context @type name description image startDate **endDate** eventStatus eventAttendanceMode location organizer **performer** url` |
| sikorski-debate | same minus `endDate` |
| christmas-dinner, youth-congress, icebreaker | same minus `endDate` and `performer` |

Polish copies additionally carry `inLanguage: "pl-PL"`, a `/pl/` `url`, and a
Polish `organizer.name`.

## 4. Event-page layout differences

The five detail pages are **not** one template.

| | business-forum | sikorski-debate | christmas-dinner | youth-congress | icebreaker |
|---|---|---|---|---|---|
| `<body>` class | **`pbf-page`** | — | — | — | — |
| Extra stylesheet | **`css/pbf.css`** | — | — | — | — |
| Hero | **`.pbf-hero`** (logo lockup, watermark, `<h1 class="sr-only">`) | `.event-hero` | `.event-hero` | `.event-hero` | `.event-hero` |
| Facts | 4 | 3 | 3 | 3 (+ `.fact-logos`) | 3 |
| Gallery grids | 2 | 2 | 1 | 1 | 0 |
| Stats band | **yes** (`.stats-grid` on a photo) | — | — | — | — |
| Founders grid | **yes** (`.pbf-people`) | — | — | — | — |
| Sponsor carousels | **2** (`.pbf-carousel-wrap`) | — | — | — | — |
| Funding note | **yes** (Senat–Polonia) | — | — | — | — |
| Ball section | **yes** (`.pbf-ball`, `.pbf-photo-row`) | — | — | — | — |
| Photographer cards | **yes** (`.pbf-photog` ×2) | — | — | — | — |
| Album card | — | — | **yes** | **yes** | — |
| Instagram embed | — | yes | yes | yes | yes |
| Co-organiser logos | — | — | — | **yes** (`.fact-logos`) | — |

**Conclusion:** the Business Forum is a separate sub-brand with its own colour
system, hero, and roughly six unique section types. Two viable approaches:

- **(a) Two templates** — a generic `event` template plus a bespoke
  `event-pbf` template. Simplest and honest about the difference.
- **(b) One template plus optional section blocks** — a Decap `list` of typed
  section widgets (gallery / prose / album / instagram / carousel / stats /
  people / funding-note). More flexible, considerably more work, and risks the
  committee assembling layouts that were never designed.

**Recommended: (a).** Treat the Business Forum as a bespoke page that the CMS
manages the *text* of, and leave its structure in the template.

## 5. How English and Polish pages are paired

The pairing is by **identical filename** across two trees. This is the invariant
the whole bilingual system rests on.

| Concern | Rule |
|---|---|
| Filenames | identical (`events.html` ↔ `pl/events.html`) — verified |
| Homepage URLs | `/` and `/pl/` |
| Shared assets | English uses `assets/…`; Polish uses `../assets/…` |
| Root-relative paths | `/favicon.ico`, `/assets/icons/…`, `/site.webmanifest` unchanged in both |
| Data files | `js/*.js` vs `js/pl/*.js` |
| Internal links | **relative** in both trees, so they stay in-language |
| Language switcher | **root-relative** (`/events.html`, `/pl/events.html`), `aria-current="true"` on the active side |
| Language detection | `<html lang>` only; no redirects, no cookies |

A generator can compute all of this from `(slug, locale)`. It must not invent a
different pairing scheme, because `hreflang`, the switcher and the sitemap all
assume it.

## 6. What a generator must preserve

### 6.1 Per-page `<head>` (20 tags, all currently present on all 22 indexable pages)

`viewport` · `description` · `canonical` · `alternate`×3 · `og:type`
`og:site_name` `og:locale` `og:locale:alternate` `og:title` `og:description`
`og:url` `og:image` `og:image:alt` · `twitter:card` `twitter:title`
`twitter:description` `twitter:image` `twitter:image:alt` · 4 `icon` links ·
`apple-touch-icon` · `manifest` · `theme-color`

### 6.2 hreflang — reciprocal, absolute, x-default = English

Both pages in a pair carry the **identical** trio; only `canonical` differs:

```html
<link rel="canonical" href="https://polsocfederation.pl/pl/events.html">
<link rel="alternate" hreflang="en" href="https://polsocfederation.pl/events.html">
<link rel="alternate" hreflang="pl" href="https://polsocfederation.pl/pl/events.html">
<link rel="alternate" hreflang="x-default" href="https://polsocfederation.pl/events.html">
```

A Polish canonical must **never** point at the English page.

### 6.3 og:locale

`en_GB` + alternate `pl_PL` on English; `pl_PL` + alternate `en_GB` on Polish.

### 6.4 Structured data

- `index.html` → `Organization`; `pl/index.html` → same plus `inLanguage: "pl-PL"`,
  `/pl/` URL, Polish `name`, English `alternateName`
- 5 event pages × 2 → `Event`, fields per §3.4
- `logo` must stay a **raster** (`/assets/icons/icon-512.png`), not the SVG
- `sameAs` must stay exactly the three confirmed Federation profiles

### 6.5 Sitemap

22 URLs (11 EN + 11 PL), absolute, both 404s **excluded**, Polish priority 0.1
below its English counterpart, valid against the sitemaps.org schema. `lastmod`
should reflect real edits — a generator that stamps today's date on all 22 pages
every build actively degrades the signal.

### 6.6 404 pages

`404.html` and `pl/404.html` carry `noindex, follow` and deliberately have **no**
canonical and **no** hreflang. They must stay out of the sitemap.

### 6.7 Things that will silently break if templated carelessly

- `data-count` / `data-suffix` / `data-plain` on stat counters (`data-plain`
  stops `2013` rendering as `2,013`)
- `.ticker` needs its `.ticker-clip` wrapper or the homepage overflows on mobile
- `.member .ph` with no `<img>` must keep `data-label` for the placeholder
- the partner carousel needs its logo set **duplicated** for a seamless loop
- `aria-current` on the active switcher link, `aria-hidden` on decorative spans
- `assets/polsocs/` logos are addressed as `../assets/…` from `pl/members.html`

## 7. Migration risks

### 7.1 Six-way duplication is the core risk — and the core prize

Each event's facts (date, venue, attendance) appear on the detail page, the
events card, the home timeline, and again in Polish. Today nothing enforces
agreement. Migration must reconcile all six copies per event and pick one truth.
Expect to find genuine discrepancies; they should be resolved by a human, not
auto-merged.

### 7.2 Translation drift

The current English and Polish trees are in sync only because they were built in
one pass. A CMS that lets an editor publish English without Polish will produce
half-translated pages. **Mitigation:** use Decap's field-level i18n (§8.3) so
invariant fields are duplicated automatically and only prose is translatable,
and treat a missing translation as "don't publish the Polish page" rather than
"publish it in English".

### 7.3 Path resolution (already bitten us once)

Relative paths inside a *data file* resolve against the **page** URL, not the
script URL. This shipped as a live bug: every announcement image 404'd on
`/pl/announcements.html` as `/pl/assets/…`. Fixed by making `image` and
`extraImages` root-relative. A generator must keep that rule, and keep
`link.href` relative — the two fields have deliberately opposite conventions.

### 7.4 Dates are display strings, not dates

`date: "7 July 2026"` / `"7 lipca 2026"` is human text with no machine value, and
announcement order is implicit array order. A CMS needs a real `date` field and
must render the localised string. Polish months take the genitive
(`7 lipca`, not `7 lipiec`) — a naive `toLocaleDateString('pl')` gets this right,
a hand-rolled month table often does not.

The Icebreaker event has **no day**, only "October 2025", and its JSON-LD uses
`startDate: "2025-10"`. The schema must permit month precision.

### 7.5 Content that must not be "translated"

An enthusiastic auto-translation pass would damage the site. The protected list
is in `docs/BILINGUAL_SITE.md` §9: event brands (Polish Business Forum, Polish
Youth Congress, Icebreaker), venues (London Business School, Ognisko Polskie,
The Landmark London, Mamuśka!), The Lambert, all universities, all sponsors, all
personal names, social handles, and quoted English conference themes.

Two prior decisions are **flagged as unconfirmed** and should be settled before
they are baked into content files: `Annual Christmas Dinner` →
`Doroczna Kolacja Wigilijna`, and the debate title →
`Jak myśleć o polityce w spolaryzowanym świecie`.

### 7.6 Body HTML

`body` is plain text with `\n\n` breaks, and exactly one entry contains raw
`<a>` markup. Moving to Markdown means re-checking that entry and deciding
whether editors may write HTML. Allowing raw HTML from a CMS is an XSS surface;
the current renderer assigns `innerHTML` directly.

### 7.7 Operational

- **No build step exists today.** Introducing a generator means the repo's
  published output no longer equals its source. Netlify must run the build, and
  contributors can no longer just open a file. Document this loudly.
- **Decap needs auth.** Git Gateway + Netlify Identity, or a GitHub OAuth app.
  Netlify Identity is deprecated for new sites — verify availability before
  committing to it.
- **Editorial workflow** creates PR branches; someone needs merge rights.
- `pl/404.html` is currently unreachable on Netlify (only root `404.html` is
  served automatically). A `netlify.toml` redirect is needed regardless of CMS.
- The repo currently has **no** `netlify.toml`, `package.json` or CI. All three
  arrive with this change.

### 7.8 Regression surface

Recent fixes are load-bearing and easy to lose in a re-template: the `.ticker-clip`
wrapper, `minmax(0, 1fr)` on `.contact-grid` / `.social-list` / `.stats-grid`,
`min(300px, 100%)` on the Instagram embed, the 2-up mobile team grid, and the
favicon block with **no** SVG icon declared. Keep the responsive sweep
(12 pages × 320/360/375/390/412/430/768/desktop, asserting
`scrollWidth <= clientWidth`) as a post-build check.

## 8. Proposed content schema

### 8.1 Storage layout

```
content/
  events/<slug>/{en,pl}.md          # or one file with i18n front matter
  announcements/<slug>/{en,pl}.md
  team/<slug>.md                    # invariants + localised role
  societies/<slug>.md               # invariants + localised uni
  pages/<page>/{en,pl}.md           # home, events, members, team, contact, 404 copy
  settings/{en,pl}.md               # nav labels, footer, UI strings
```

Media stays where it is: `assets/announcements/`, `assets/team/`, `assets/pbf/`,
`assets/polsocs/`, `assets/debata/`, `assets/wigilia/`, `assets/yc/`.
**Do not** relocate — every existing path and the OG image depend on them.

### 8.2 Event

```yaml
slug: business-forum            # → event-<slug>.html and pl/event-<slug>.html
template: pbf | standard        # picks the layout (see §4)
order: 1                        # newest first on events.html
start_date: 2026-04-24          # ISO; date-only allowed
end_date: 2026-04-25            # optional
date_precision: day | month     # icebreaker needs "month"
venue_name: London Business School
locality: London
country: GB
hero_image: /assets/pbf/stage.jpg
hero_image_alt: <localised>
flagship: true
facts:                          # 3–4 label/value pairs, both localised
  - { label: Date, value: "24–25 April 2026" }
og_image: /assets/pbf/stage.jpg
# localised:
title: Polish Business Forum 2026
card_summary: <text for events.html>
timeline_summary: <one line for index.html>
body: <markdown>
seo_title / seo_description
schema_description: <JSON-LD description>
performers: [ { name: Jan Krzysztof Bielecki } ]   # invariant
gallery: [ { image, alt } ]
instagram_permalink: https://www.instagram.com/p/…  # optional
album: { url, title, description }                  # optional
```

Generating an event writes **six** artefacts: two detail pages, two cards on
`events.html`/`pl/events.html`, two timeline rows on the homepages. That is the
duplication problem solved at the source.

### 8.3 Field-level i18n (the drift fix)

Decap supports `i18n: true | duplicate | none` per field. Use it deliberately:

| `i18n` | Use for |
|---|---|
| `duplicate` | `slug`, dates, coordinates, image paths, `performers`, `flagship`, `order`, society `lat`/`lng`/`email`/`instagram`/`logo`/`name`, team `email`/`linkedin`/`photo` |
| `true` | every prose field: titles, summaries, body, SEO text, alt text, fact labels/values, `role`, `uni` |
| `none` | fields that exist only in English, if any |

`duplicate` means the editor types it once and both locales stay identical **by
construction** — which is exactly the guarantee §7.2 needs and that hand-editing
cannot provide.

Top-level config:

```yaml
i18n:
  structure: multiple_folders
  locales: [en, pl]
  default_locale: en
```

### 8.4 Announcement

```yaml
slug, order
date: 2026-07-07                 # real date; rendered per locale
image: /assets/announcements/become-a-trustee.jpg   # nullable, root-relative
image_position, image_fit, image_background          # optional
extra_images: []                                     # root-relative
signups_closed: false
link: { event: <event slug> | external_url, label }  # see note
# localised: title, subtitle, body (markdown)
```

**Note on `link`:** store the *event slug*, not a path. The generator emits a
relative `event-<slug>.html` for English and the same relative string for Polish,
which resolves inside `/pl/`. Storing a raw path invites the §7.3 bug back.

### 8.5 Team member

```yaml
slug, group: trustees|partnerships|events|marketing|legal|regional
order
name                     # duplicate
photo                    # duplicate, nullable → renders the placeholder
email, linkedin          # duplicate
# localised: role, photo_alt
```

### 8.6 Society

```yaml
name, lat, lng, instagram, email, logo,
active, member, past_member          # all duplicate
# localised: uni
```

Rendered output must remain a JS array (or JSON) that the existing Leaflet code
can consume, unless that code is rewritten too.

### 8.7 Site settings / page copy

Nav labels, footer text, the four `main.js` UI strings, hero copy, FAQ entries,
testimonials, stat labels. Lowest priority — do this only after the four main
collections are stable.

## 9. Suggested sequencing

1. **`netlify.toml` + `/pl/*` 404 redirect** — needed anyway, independent of CMS.
2. **Generator skeleton** that reads the *existing* JS data files and re-emits
   today's `announcements.html` / `members.html` byte-for-byte. Proves the
   pipeline without touching content.
3. **Announcements + societies → content files.** Lowest risk, already structured.
4. **Team → content files.** Single page per language, mechanical extraction.
5. **Events last**, and reconcile the six copies by hand as part of it.
6. **Decap config + auth**, then page copy and settings.
7. Keep the responsive + SEO validation sweep as a build check throughout.

Steps 1–3 are safely reversible. Step 5 is the one that needs care.

## 10. Open questions for the committee

1. Who administers the CMS, and who may merge? (editorial workflow needs a
   reviewer)
2. Netlify Identity vs GitHub OAuth — Identity is deprecated for new sites.
3. Should editors be able to create a **new event**, or only edit existing ones?
   Creating one currently implies a new URL, sitemap entry and hreflang pair.
4. May editors publish English-only, or is a Polish translation mandatory before
   publish? (§7.2 — recommend mandatory, or auto-unpublish the Polish page.)
5. Confirm the two flagged translations in §7.5.
6. Is raw HTML allowed in announcement bodies, or Markdown only? (§7.6)
